
# Практична робота №18
# Надійність, кешування та спостережуваність

## 1. Мета роботи

Забезпечити надійну роботу AI Study Assistant
під час тимчасових збоїв AI-провайдера,
пошукового компонента RAG, файлової системи
та локального сховища.

Реалізувати механізми контролю часу,
повторних спроб, обмеження навантаження,
кешування, журналювання й аналізу помилок.

## 2. Використані технології

- Python
- FastAPI
- Ollama
- Qwen3:4b
- Qwen3 Embedding 0.6B
- HTTPX
- SQLite
- RAG
- pytest
- JSON Lines
- SHA-256

## 3. Архітектура системи

Користувач працює через вебінтерфейс StudyAI.

Запит надходить до FastAPI, після чого
створюється фонове завдання.

StudyService завантажує навчальні документи,
виконує RAG-пошук і передає контекст
до Orchestrator.

Orchestrator використовує Gateway
для звернення до AI-моделі.

Gateway відповідає за:

- перевірку дедлайну;
- повторні спроби;
- контроль бюджету;
- Circuit Breaker;
- обмеження одночасних викликів;
- журналювання.

Результати та контрольовані помилки
зберігаються у SQLite.

## 4. Карта залежностей і збоїв

| Компонент | Можливий збій | Реакція |
|---|---|---|
| Ollama LLM | Timeout | Обмежений повтор |
| Ollama LLM | HTTP 429 | Retry-After та повтор |
| Ollama LLM | HTTP 5xx | Повтор і Circuit Breaker |
| Ollama LLM | HTTP 401/403 | Без повтору |
| Ollama LLM | Некоректна відповідь | Контрольована помилка |
| Embedding-модель | Недоступність | Помилка RAG |
| RAG-індекс | Відсутній файл | Спроба побудови індексу |
| RAG-індекс | Пошкодження | Контрольована помилка |
| SQLite | Помилка запису | Контрольована відмова |
| FastAPI | Перевищення частоти | HTTP 429 |
| Gateway | Зайняті всі місця | HTTP 429 |
| AI | Вимкнення функції | Помилка ai_disabled |

## 5. Тайм-аути

У проєкті передбачено:

1. Тайм-аут одного HTTP-звернення.
2. Тайм-аут очікування даних.
3. Загальний дедлайн AI-сценарію.

Реалізація:

`app/deadlines.py`

Для визначення залишку часу використовуються:

- request_deadline()
- remaining_seconds()
- check_deadline()
- bounded_timeout()
- http_timeout()

Загальний дедлайн обмежує послідовність:

Завантаження документів → RAG → LLM → перевірка.

Остаточні значення тайм-аутів необхідно
обґрунтувати фактичними вимірюваннями p95.

## 6. Повторні спроби

Реалізація:

`app/gateway.py`

Підтримуються:

- exponential backoff;
- jitter;
- Retry-After;
- перевірка загального дедлайну;
- обмеження кількості спроб.

Автоматичні повтори дозволено для:

- timeout;
- rate_limit;
- provider_unavailable.

Повтори не виконуються для:

- auth;
- bad_request;
- помилок валідації;
- постійних збоїв конфігурації.

У Gateway за замовчуванням передбачено
не більше двох спроб на один виклик.

Важливо: додаткова генерація після
невалідного результату в Orchestrator
може збільшити загальну кількість звернень.

Сумарну межу викликів необхідно перевірити
окремим автоматизованим тестом.

## 7. Circuit Breaker

Реалізація:

`app/reliability.py`

Передбачені три стани:

- closed — запити дозволені;
- open — виклики тимчасово блокуються;
- half_open — дозволено один пробний виклик.

Circuit Breaker враховує помилки:

- timeout;
- provider_unavailable;
- rate_limit.

Не враховує помилки:

- auth;
- bad_request;
- invalid_output.

Стан запобіжника доступний
через метод Gateway.health().

FastAPI повертає його у:

GET /api/health

Перевірка health не повинна
створювати новий виклик Ollama.

## 8. Обмеження частоти та одночасності

Реалізація:

`app/reliability.py`

Використовується SlidingWindowRateLimiter.

Власний ліміт обмежує кількість
HTTP-запитів від одного клієнта.

При перевищенні повертається:

- HTTP 429;
- kind: client_rate_limit;
- retryable: true;
- Retry-After.

Для обмеження одночасних звернень
до AI використовується BoundedSemaphore.

Якщо всі місця зайняті,
повертається контрольована помилка
concurrency_limit.

Обмеження поточної реалізації:
ліміт частоти зберігається в пам'яті
одного процесу FastAPI.

## 9. Вимикач AI-функції

Налаштування:

AI_ENABLED=true

або

AI_ENABLED=false

Якщо AI_ENABLED=false, StudyService
повинен припиняти AI-сценарій
до виконання RAG і LLM.

Контрольована помилка:

- kind: ai_disabled;
- HTTP 503;
- retryable: false.

Вимикач дозволяє тимчасово припинити
генерацію без зупинки всього вебсервера.

## 10. Безпечні помилки

Основна модель помилок:

AppError

У відповіді користувачу передаються:

- kind;
- message;
- retryable;
- request_id;
- Retry-After, якщо потрібно.

Не повинні передаватися:

- traceback;
- API-ключі;
- паролі;
- повні промпти;
- приватні дані документів;
- внутрішні повідомлення винятків.

Для непередбачених збоїв
використовується загальна помилка internal_error.

## 11. Структуроване журналювання

Реалізація:

`app/telemetry.py`

Формат:

JSON Lines

Основний файл:

`logs/app.jsonl`

Поля журналу:

- ts;
- request_id;
- layer;
- event;
- provider;
- model;
- prompt_version;
- schema_version;
- attempt;
- duration_ms;
- status;
- error_kind;
- cached;
- fallback;
- input_tokens;
- output_tokens;
- cost.

Записуються лише дозволені
службові метадані.

Журнал не повинен містити:

- текст запитання користувача;
- відповідь AI;
- секрети;
- вміст навчальних документів.

Передбачено ротацію файлів журналу.

Папка logs/ повинна бути виключена з Git.

## 12. Кешування

Реалізація:

- `app/rag/cache.py`
- `app/rag/embedder.py`

Кешуються embedding-вектори.

Готові відповіді AI-моделі
не кешуються цим механізмом.

Тип кешу:

In-memory TTL cache.

Початкові параметри:

- TTL: 3600 секунд;
- максимум: 2048 записів.

Ключ залежить від:

- SHA-256 тексту;
- назви embedding-моделі;
- версії моделі;
- адреси сервера;
- ідентифікатора власника.

Підтримуються:

- cache hit;
- cache miss;
- TTL;
- обмеження кількості записів;
- інвалідація власника;
- обхід кешу;
- захист від кешування помилок.

Після перезапуску процесу кеш очищується.

Для локального одноосібного використання
можна ввімкнути:

STUDYAI_EMBED_CACHE_ENABLED=1

STUDYAI_EMBED_CACHE_OWNER=local-studyai

У багатокористувацькому режимі
owner_id необхідно отримувати
з перевіреної автентифікації.

## 14. Сценарії навмисних збоїв

| Сценарій | Очікуваний результат |
|---|---|
| Timeout LLM | Контрольований повтор |
| HTTP 429 | Урахування Retry-After |
| HTTP 401 | Відсутність повтору |
| Вичерпаний дедлайн | Зупинка повторів |
| Недоступна Ollama | Контрольована помилка |
| Тривалі збої | Circuit Breaker open |
| Відновлення провайдера | Half-open → closed |
| Недоступні embeddings | Помилка RAG |
| Збій embeddings | Помилка не кешується |
| Повторний текст | Cache hit |
| Обхід кешу | Новий виклик |
| AI_ENABLED=false | Генерацію заблоковано |

Тестування на підставному провайдері
не замінює перевірку справжньої Ollama.

## 15. Аналіз журналу

Скрипт:

`eval/pr18_analyze.py`

Команда:

    python eval/pr18_analyze.py

Результат:

`docs/pr18_analysis.md`

Аналізатор обчислює:

- кількість запитів;
- кількість викликів провайдера;
- кількість повторів;
- успішні повтори;
- помилки за видами;
- p50;
- p95;
- токени;
- наявні дані кешу;
- записану вартість.

Якщо певна метрика відсутня,
звіт повинен показати
«немає даних».

Відсутність записів про вартість
не означає, що витрати дорівнюють нулю.

## 16. Відомі обмеження

Перед завершенням ПР18 необхідно перевірити:

1. Повну сумісність змін із ПР15–ПР17.
2. Сумарну кількість звернень до LLM.
3. Реальне дотримання тайм-аутів HTTP.
4. Поведінку Circuit Breaker при збоях.
5. Перевірку стану кожної мережевої залежності.
6. Коректне збереження Retry-After.
7. Відсутність конфіденційних даних у журналі.
8. Показники кешу під час реального використання.
9. Фактичні p50/p95 Ollama.
10. Роботу системи після перезапуску.

У межах практичної роботи №18
для AI Study Assistant підготовлено
механізми підвищення надійності:

контроль часу, повторні спроби,
Circuit Breaker, обмеження частоти
та одночасності, безпечні помилки,

від успішного проходження повного набору
тестів та перевірки реальних вимірювань.
