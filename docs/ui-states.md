# ПР17 — Стани користувацького інтерфейсу

## 1. Вибір технології

Інтерфейс реалізується на HTML, CSS та JavaScript.

Сторінка обслуговується тим самим FastAPI-сервером.

Причини:
- Не потрібно створювати окремий фронтенд-проєкт.
- Запити виконуються через API ПР14.
- Не потрібне окреме налаштування CORS.
- Простіше тестувати й розгортати застосунок.

## 2. Основний сценарій

1. Користувач відкриває сторінку.
2. Бачить призначення застосунку та приклад.
3. Вводить запитання.
4. Браузер перевіряє введені дані.
5. Запитання надсилається через POST /api/ask.
6. Сервер повертає request_id.
7. Інтерфейс перевіряє стан через GET /api/requests/{request_id}.
8. Після завершення показується перевірена відповідь.
9. Користувач може скопіювати або зберегти результат.
10. Історію запиту можна відкрити повторно за request_id.

## 3. Стани екрана

### Порожній стан
- Видно назву застосунку й коротке пояснення.
- Показано приклад запитання та обмеження.
- Доступне поле введення.
- Перехід: початок введення.

### Введення
- Користувач вводить запитання.
- Доступне очищення тексту.
- Надсилання доступне лише для коректного введення.
- Перехід: перевірка введення.

### Помилка введення
- Повідомлення розміщується поруч із полем.
- Введений текст зберігається.
- Перехід: користувач виправляє запитання.

### Запит прийнято
- Сервер повернув HTTP 202 і request_id.
- Кнопка надсилання заблокована.
- Перехід: отримання поточного стану завдання.

### Очікування
- На екрані показано стан pending або running.
- Доступне скасування запиту.
- request_id зберігається для відновлення.
- Перехід: завершення, помилка або скасування.

### Результат
- Показується лише перевірена відповідь.
- Окремо відображаються джерела.
- Доступне копіювання та збереження тексту.
- Перехід: нове запитання або повтор.

### Недостатньо даних
- Показано стан no_evidence.
- Пояснено, що підтверджених даних недостатньо.
- Користувач може уточнити запитання.

### Контрольована помилка
- Показано зрозуміле повідомлення.
- Показано request_id.
- Повтор доступний лише для retryable=true.
- Введений текст не видаляється.

### Помилка з'єднання
- Пояснено, що зв'язок із сервером втрачено.
- Збережено введення та відомий request_id.
- Доступне повторне підключення.

### Скасовано
- Показано стан cancelled після підтвердження сервера.
- Користувач може створити новий запит.

### Повторний запит
- Створюється нове завдання.
- Попередній результат не видаляється зі сховища.
- Користувач контролює повторну генерацію.

## 4. Межі введення

Межі потрібно отримувати з OpenAPI-схеми сервера.

Поточна модель AskInput:
- question: від 1 до 500 символів;
- documents: від 1 до 5 документів.

Сервер залишається остаточним джерелом правил.

## 5. Відображення виконання

Використовується фонова задача й опитування API.

Маршрути:
- POST /api/ask;
- GET /api/requests/{request_id};
- POST /api/requests/{request_id}/cancel.

Проміжні етапи RAG, генерації та перевірки
можна відображати лише після отримання
відповідних подій або станів від сервера.

## 6. Безпека

- Текст AI вставляється через textContent.
- Дані користувача не виконуються як HTML.
- Секретні ключі не передаються у JavaScript.
- Валідація виконується на сервері.
- Повідомлення не містять внутрішніх traceback.

## 7. Доступність

- Поля мають текстові підписи.
- Помилки пов'язані з відповідними полями.
- Інтерфейс працює з клавіатури.
- Стани позначаються текстом, а не лише кольором.
- Для зміни станів використовується aria-live.

## 8. Редагування та підтвердження

AI Study Assistant надає інформаційні відповіді
за навчальними документами.

Результат не виконує зовнішніх дій,
тому окреме підтвердження такої дії не потрібне.

Користувач може змінити запитання і створити
новий варіант відповіді.

Для результату потрібні копіювання та збереження,
а не редагування фінансових чи інших
структурованих даних.

## 9. Перевірка

Необхідно протестувати:
- порожнє запитання;
- задовге запитання;
- успішну відповідь;
- no_evidence;
- збій AI-провайдера;
- втрату з'єднання;
- скасування;
- відновлення після оновлення сторінки;
- захист від подвійного надсилання;
- коректне відображення недовіреного тексту.
